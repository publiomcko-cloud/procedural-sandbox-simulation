## Implementation / security summary

Double-clicking `Launch-F2SandboxReadiness.cmd` runs the host launcher. It stages exactly two strict-UTF8/hash-pinned PowerShell files into `C:\F2-Approved-Inputs`, validates the automation `.wsb`, writes a GUID-named configuration under TEMP, and presents its complete scope in a Yes/No dialog. It refuses to update mapped inputs while `WindowsSandbox.exe` is active. The guest mapping remains read-only; Networking, clipboard, vGPU, audio, video and printer redirection remain disabled; ProtectedClient remains enabled. The one accepted `LogonCommand` launches only the pinned bootstrap.

The bootstrap runs as the Sandbox container administrator only to create a uniquely named guest-local ordinary user. It uses the cryptographic RNG and a SecureString; password characters are cleared, and no password is saved, printed, or passed as process arguments. The bootstrap then launches only the pinned diagnostic with `Start-Process -Credential`, verifies the resulting identity and `WindowsPrincipal.IsInRole(Administrator) == false`, and prints a compact report. Any setup/identity error yields `BLOCKED_STANDARD_USER` with no administrator fallback. The reviewed command prints a banner before invoking the bootstrap and uses `-NoExit`, so startup errors and the final report remain visible until the owner closes the window or Sandbox. Errors are reduced to stage, sanitized category/type, and child exit code when known. Child execution has a 60-second timeout; this does not claim CPU/disk or the proposed 5-minute/30-minute session supervision.

No Godot/Voxel Tools download, extraction, or execution. No host account, OS feature, persistent policy, or security configuration change. The host PowerShell `ExecutionPolicy Bypass` arguments are per-process only. No network/clipboard/vGPU relaxation or writable host mapping. Account and output temp files are guest-local; user and temporary output files are removed at the end, and the owner discards the Sandbox normally.
