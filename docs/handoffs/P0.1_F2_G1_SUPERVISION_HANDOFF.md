## Feasibility conclusions

- Windows Sandbox is **not feasible for the mandatory hard-gated G1 run as currently configured**: its documented `.wsb` controls do not provide CPU, disk quota, or wall-clock session enforcement. `MemoryInMB`, free-space monitoring, and a read-only host mapping do not replace those controls. Job Objects can constrain an associated child tree but not all guest activity.
- A pre-provisioned offline throwaway VM is the preferred candidate if it can provide a queried-back CPU/memory cap, independent <=30-minute host watchdog, fixed-size OS and scratch VHDX, no network device or enhanced-session redirection, standard-user execution, and a read-only verified input. This route is not present or validated by this task; if it needs feature installation/admin action or any gate cannot be enforced, stay `BLOCKED_ENVIRONMENT`.
- The first Issue #43 screenshot at source-associated HEAD `cc2feb14...` had no child exit code and showed the old misleading `DiagnosticGateFailed`; the later Issue #44 screenshot reports child exit code `0` and `ReadinessGatesRemainUnknown`, consistent with corrected source at `dfcd264...`. The screenshot does not cryptographically attest the exact guest source/configuration; observations are tied to the owner-reported screenshot/run, not a verified guest SHA. The later screenshot proves only its reported diagnostic child token, zero adapters/routes, read-only mapping, and adapter inventory. Future Godot token, all network pathways, GL, supervision, evidence/discard, and native runtime remain unknown/not run.
- Host watchdog/reaper startup, VM identity binding, controller loss, missed deadline, stop failure, and confirmed named-VM cessation are explicit fail-closed gates and inert fault cases. Neither watchdog layer is implemented, provisioned, or observed; until independent expiry/reaper behavior passes, the session limit remains `UNKNOWN` and VM/native work remains `BLOCKED_ENVIRONMENT`.
- Renderer feasibility is `UNKNOWN`; the future target is the exact official native editor executable, with identity/hash, runtime `gl_compatibility` method, `get_current_rendering_driver_name()`, and actual backing API/device recorded. `opengl3_angle` requires evidence of the underlying ANGLE/D3D11 device; the native-export D3D11 requirement cannot be transferred to the editor. No forced Forward+/Vulkan fallback.
- Proposed numeric limits are initial design ceilings, not owner-approved or demonstrated runtime guarantees. The inert matrix must prove actual enforcement before any native stage.

## Limitations and risks

- Job Objects cover associated processes; process creation methods that bypass normal job inheritance and guest OS activity need separate detection/control. Failure to prove containment is a blocker, not a reason to label monitoring as enforcement.
- Fixed-size VHDX caps virtual capacity, but suitability, guest volume layout, and disk-full handling are unverified.
- Godot GL Compatibility under a vGPU-disabled disposable VM/Sandbox is untested. A Remote Display Adapter inventory, driver string, or export-only D3D11 support is not native-editor proof.
- The primary host watchdog and independent expiry/reaper have not been implemented, provisioned, or failure-injection tested.
- No evidence export/disposal route has been owner-confirmed.
- The candidate ceilings require independent technical review and owner acceptance before implementation; they are not performance claims.
