- Use a unique disposable guest project, TEMP, Godot user-data/cache roots, and run ID outside every `C:\Dev\sandbox-sim-*` worktree. Canonicalize paths and reject reparse points. Never extract or execute archive contents on the host.
- If the future G1 owner-approved stage uses the pinned Voxel Tools archive, require the exact Issue #26 asset URL, size `54,457,774` bytes, SHA-256 `600737572a5e25541ba6f503e842a3717ba19afafa5474510a6ceff995a1d2d8`, and source commit `75d3c6d996ed2331c80edcd8c3ebc947afc0f041`. Verify the exact official Godot `4.7.2.stable.official.ed1daf0bf` x86_64 build identity. Rehash and rerun the accepted ZIP safety preflight inside the guest before extraction; use no vendor installer/build script, additional download, or unapproved dependency.
- Keep the smoke/probe <=5 minutes and full session <=30 minutes, with bounded process count, CPU/memory, logs and disk as designed below. Detect unexpected subprocesses, network paths, files, or writes and stop. Preserve the failed record; never silently continue or claim an unobserved limit.

After verified export, close/discard the exact guest normally and remove only verified per-run disposable paths; if identity, containment, export, or cleanup is uncertain, preserve the evidence and report `INCONCLUSIVE`/`BLOCKED_ENVIRONMENT` rather than recursively deleting an unchecked path.

### Evidence vocabulary

| State | Meaning |
|---|---|
| `OBSERVED_PASS` | Direct evidence for the narrowly stated property and run; does not imply a broader property. |
| `CONFIGURATION_ONLY` | Static source/configuration is correct; the setting's runtime effect was not observed. |
| `UNKNOWN` | Evidence is absent, ambiguous, or insufficient. It is a blocking state for a hard prerequisite. |
| `FAIL` | An observed condition violates a hard gate or an enforcement test fails. |
| `NOT_RUN` | An intentionally unexecuted action or probe. |

## 3. Resource supervision design

### 3.1 Guest-local child supervisor

The future supervisor is a small, reviewed, guest-local controller launched as the randomized standard guest user. It has a fixed allowlist containing only the exact approved official Godot path and the selected inert fixture executables during supervisor qualification. It accepts no free-form command, shell string, URL, or user-selected executable. It writes only bounded sanitized records into the disposable guest evidence directory.

For each child run, the controller should:

1. Resolve and canonicalize the approved executable and working directory; reject reparse points, unexpected files, unknown hashes, and paths outside the disposable guest volume plus the read-only input mapping.
2. Open the expected standard user's token, verify its SID and that Administrators is absent/disabled, and create the child suspended under that token. Do not use an administrator fallback. Keep credentials randomized, guest-local, transient, absent from command lines/logs, and clear managed password material promptly.
3. Create an unnamed, non-inheritable Windows Job Object and set every supported limit before resuming the child. Assign the suspended process first. Verify the assignment and query back the applied limits; inability to create, set, query, or assign any required limit fails closed.
4. Set neither `JOB_OBJECT_LIMIT_BREAKAWAY_OK` nor `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`; set `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`; apply job-wide committed memory, active-process count, per-job user-time, and CPU hard-cap controls. Use a completion port or equivalent bounded event loop to record limit events and process exits.
5. Keep the only job handle in the supervisor, non-inheritable. On child timeout, operator cancellation, or supervisor failure, closing the last handle must terminate the entire attached tree. Process creation that escapes job association (including non-`CreateProcess` creation paths) must be detected by the inert fixtures or treated as an enforcement failure; do not claim tree coverage based solely on polling the original PID.
6. Bound captured stdout/stderr and report files; reject oversized output rather than truncating away failure indicators. The report always includes child exit code or `UNKNOWN`, timeout/cancel state, job counters, effective token evidence, executable path/hash, and each gate's exact status.

Candidate initial ceilings for a future owner-reviewed VM diagnostic (not measured or yet owner-approved):

| Limit | Proposed ceiling | Enforcement mechanism / stop condition |
|---|---:|---|
| Per child wall-clock | 5 minutes | Monotonic supervisor deadline; expiry closes/terminates the child job. Missing timer, supervisor hang, or surviving child is `FAIL`. |
| Whole session wall-clock | 30 minutes | Independent host-side VM watchdog powers off only the named disposable VM at deadline; if there is no independent watchdog, the session gate remains `UNKNOWN`. |
| VM CPU capacity | 2 virtual CPUs, 20% maximum | Hypervisor VM processor count and hard maximum, captured/query-verified before start. This caps the VM separately from the child Job Object CPU cap. |
| VM memory | 8 GiB fixed maximum; dynamic memory disabled | Hypervisor static startup/maximum memory, queried back before start. The job still has its separate 4-GiB aggregate committed-memory limit. |
| Job committed memory | 4 GiB aggregate | Job-wide memory limit, queried back and tested with inert allocation. Allocation failure is reported as a limit event. |
| CPU rate | 20% of guest's available CPU capacity | Job CPU hard cap; query back and verify with a CPU-burn fixture. Sampling Task Manager is not proof. |
| Active process count | 32 | Job active-process limit; a child creation attempt at the cap must fail/terminate predictably. |
| Captured stdout / stderr | 4 MiB each | Bounded byte counters; overflow is a fail-closed run failure. |
| Disposable storage | OS VHDX 64 GiB fixed + scratch VHDX 8 GiB fixed | Only attached writable disks; no checkpoints/differencing disk growth, pass-through, writable host maps, or extra writable devices. Verify attached disk identities, capacities, volume layout, and free space before the run. |

These are design ceilings, not proven suitability for Godot. Any future change needs an explicit reviewed rationale and a new exact-source review; values may not be silently raised to get a test to pass. Job Objects constrain associated processes, not the entire guest OS. Their CPU and process/memory settings must be queried back and tested on the actual supported Windows build. The VM's separate processor/memory caps and 30-minute limit therefore need an independent host controller. The VM's virtual disk layout must cap all guest-writable storage. A fixed VHDX has its capacity allocated and does not grow when data is added; filling it must produce an explicit failure rather than unbounded host growth.

### 3.2 Sandbox versus throwaway VM

| Safeguard | Windows Sandbox | Pre-provisioned throwaway VM |
|---|---|---|
| Offline and no clipboard/vGPU | Supported by exact `.wsb` settings; effective run configuration still must be captured. | Possible with no virtual NIC and no enhanced-session clipboard/drive/printer integration; inspect effective VM/device configuration each run. |
| Read-only inputs | Narrow read-only mapped folder is supported; keep exact current mapping. | Attach a copied, hash-verified input as read-only media; no host filesystem share. |
| Process-tree limits | Guest Job Object can constrain an attached child tree, but not the guest OS or every possible child-creation path. | Same guest Job Object limits, with an external controller able to stop only the named disposable VM on session timeout or supervisor failure. |
| CPU/session ceilings | `.wsb` exposes no CPU quota or session deadline. Guest process limits do not cap whole guest CPU or OS work. | VM processor count/max (proposed 2 vCPU / 20% cap) plus independent host watchdog are configurable on a pre-provisioned Hyper-V VM. Effective settings require query-back and inert proof. |
| Disk cap | `.wsb` exposes no disk-size/quota setting. MemoryInMB is unrelated; free-space checks are telemetry only. | Fixed-size OS and scratch VHDX provide finite virtual capacities; use no dynamic/differencing/checkpoint disks and prove volume-full behavior on a small inert fixture disk. |
| GL with vGPU disabled | WARP/software rendering is used when vGPU is disabled; Remote Display Adapter inventory does not establish OpenGL 3.3 or Godot readiness. | A dedicated virtual display/adapter may or may not expose the required OpenGL 3.3 path; remains unknown until tested with the exact renderer under all gates. |
| Current disposition | `BLOCKED_ENVIRONMENT` for Issue #26 hard CPU/disk/time gates. Do not stage or launch native payloads. | Preferred candidate only if already provisioned without host security/feature changes and all controls can be independently queried and inert-tested. Otherwise `BLOCKED_ENVIRONMENT`. |

Hyper-V/admin features must not be enabled or installed by this task. If the owner cannot provide an already available VM with the required offline configuration, quotas, storage and access, stop and report `BLOCKED_ENVIRONMENT`; do not fall back to Sandbox or host execution.

## 4. Standard-user and process-token attestation

The current bootstrap's temporary standard-user diagnostic remains useful as one input only. Before any future Godot run, the supervisor must use the randomized guest-local standard account and verify the actual created process, not an unrelated shell:

- Record the expected local SID before start; use a suspended process creation path for that account and assign the process to the configured Job Object before resume.
- Query the process token by its verified PID and handle. Record user SID, group SIDs/attributes (especially Administrators), token elevation type/elevated flag, integrity SID/level, session ID, and whether it is an AppContainer if applicable.
- Confirm executable final path and SHA-256 against the separately reviewed official Godot 4.7.2 Windows x86_64 artifact identity. Also record file version/product version and process creation time to bind evidence to that instance. No password or credential material enters evidence.
- Recheck token and image identity while the process is live and bind the final exit code/report to the same PID/creation time. PID reuse, access denied, unavailable token fields, unexpected child, admin/elevated token, or hash/path mismatch fails closed.
- Include a positive inert fixture under the expected user and negative fixtures for an administrator token, wrong SID, wrong binary hash/path, failed Job Object assignment, and unavailable token query. No actual Godot process is started in Issue #44.

## 5. Godot 4.7.2 GL Compatibility feasibility procedure

This procedure is future-only, after the isolation, offline, process/job, disk, time, and evidence gates pass. No Godot binary is executed by this issue.

1. Use only the official `4.7.2.stable.official.ed1daf0bf` Windows x86_64 build specified by Issue #26. Record and verify its approved SHA-256 and final guest path after read-only staging; do not execute it on the host.
2. Keep vGPU disabled and all networking, clipboard, writable host mappings, and redirections disabled. Use a minimal disposable clean project on the capped guest scratch volume, with user data/cache/TEMP redirected into that volume. No Voxel Tools files are present for this renderer-only check.
3. Pin the project renderer setting to `gl_compatibility`, pass `--rendering-method gl_compatibility` explicitly, and capture the unedited Godot startup log plus `RenderingServer.get_current_rendering_method()` from a reviewed minimal project script. Require the reported actual method to equal `gl_compatibility`; a command-line request by itself is not proof because renderer fallback is possible.
4. Capture the actual OpenGL vendor/renderer/version from the engine startup log and require the supported Windows Compatibility path (Godot 4.7 documents full OpenGL 3.3 or Direct3D 11 compatibility support); record whether rendering is WARP/software or a virtual display device. Run a minimal visible GUI scene, capture the guest screen through the owner-controlled evidence procedure, then exit cleanly within 5 minutes.
5. Treat inability to initialize GL Compatibility, silent fallback to another renderer/driver, missing actual renderer/API evidence, vGPU requirement, or crash as `BLOCKED_RENDERER`/`FAIL`. Do not enable vGPU, switch to Vulkan/Forward+, use a custom Godot build, or infer readiness from adapter inventory.

The actual renderer may be automatically changed by a fallback; therefore both the requested method and runtime-reported method/log are required. Godot's 4.7 system requirements describe Windows Compatibility support in terms of OpenGL 3.3 or Direct3D 11, while its renderer documentation identifies Compatibility as the OpenGL renderer. A Remote Display Adapter name alone cannot satisfy either runtime check.

## 6. Evidence capture, export and disposal

Evidence must be useful to review while revealing no guest credentials, user profile content, unrelated paths, tokens, or secrets.

1. Before a future session, assign a random run ID and record the approved config hash, VM identity, exact read-only input hashes, guest image identity, effective network/device/disk/CPU/memory configuration, UTC timestamps, and reviewer-approved output allowlist. Do not record the randomized password.
2. During execution, capture the visible guest window using an owner-controlled host screenshot path. Save only sanitized supervisor JSON/text logs and the screenshot; exclude environment dumps, command lines with secrets, full profiles, unrelated directory listings, clipboard data, crash dumps containing memory, and arbitrary guest files.
3. Since clipboard and writable host shares remain disabled, use only a specifically approved, one-way evidence mechanism: owner screenshots plus, for a VM, detach the exact scratch VHDX after guest shutdown, mount it read-only on the host, and copy only manifest-listed sanitized log files after path/content review. Do not add an evidence output mapped folder or enable an enhanced-session channel. Windows Sandbox currently has no approved sanitized log export route under these constraints; screenshots alone leave log archival/disposal `UNKNOWN` until the owner approves and verifies another safe method.
4. Before shutdown, confirm child process tree empty, final child exit status known (or explicit `UNKNOWN`), logs flushed and size-bounded, and evidence manifest SHA-256 generated. Review/sanitize the capture on the host before adding it to the evidence record.
5. Owner normally shuts down/discards the guest. For a VM, power off the exact disposable VM through its named host controller after the 30-minute deadline or a supervisor-failure event; no broad host process termination. Remove only the exact run's disposable disks/checkpoints after identity/path/content verification and after evidence hash verification. Retain only sanitized evidence and its manifest.
6. Owner confirms no VM/Sandbox process remains, no guest disk is still attached, no mapped input was changed, and the only retained artifacts are reviewed evidence. Until that confirmation, `Evidence export/discard` remains `UNKNOWN`.

## 7. Inert-only enforcement qualification strategy

All actual enforcement proof must occur in the future disposable, offline, standard-user guest/VM and use only first-party inert fixtures that print bounded markers, sleep, spawn controlled child processes, allocate bounded memory, consume CPU, and write synthetic bytes to the scratch volume. No Godot, Voxel Tools, DLL, vendor code, network fixture, or native F2 probe is included. Source assertions and mocks are useful CI checks but do not prove OS enforcement.

| Fixture | Safe expected result | Fail/stop condition |
|---|---|---|
| Allowlisted inert child, standard-user token | Starts suspended, is assigned before resume, reports expected SID/nonadmin token and known hash/path, exits zero. | Any missing token evidence, admin/elevated token, hash/path mismatch, or unassigned running child. |
| Child spawns ordinary descendants | Parent, child and grandchild all appear in same job; job counters match; normal exit leaves none. | Any descendant outside the job or unaccounted PID. |
| Deliberate breakaway / alternate process-creation attempt | The API attempt is denied or the external VM controller detects and stops the named disposable VM; report is fail-closed. | Escaped live process or inability to prove teardown. |
| Wall timeout / cancellation | A short test-only deadline first validates event handling; a separate bounded run validates the configured <=5-minute production deadline. Every job member exits after last job-handle closure. | Any survivor, lost timeout event, or unbounded wait. |
| Supervisor crash | Inert supervisor intentionally exits while children are in the job; last-handle close kills them. Independent VM watchdog enforces <=30-minute session bound. | Child survives or host watchdog cannot identify/stop only the named VM. |
| CPU and memory ceiling | CPU-burn fixture observes job hard cap; allocation fixture reaches queried-back 4-GiB aggregate job limit and receives expected failure/limit event. | Only sampled telemetry, non-enforced limit, unhandled allocation failure, or job settings differ from queried values. |
| Process-count/output limits | Spawn and output fixtures reach configured limits; run becomes a bounded, explicit failure with no log growth beyond cap. | Excess processes/output continue or diagnostic evidence truncates away the reason. |
| Disk cap | On a separate small fixed-size scratch test VHDX, bounded synthetic writes reach volume full; all writes remain on that volume; guest reports the expected error without touching host mappings. | Disk grows past the declared size, writes land outside scratch, or full-volume behavior is not observable. |
| Missing/malformed supervisor result | Remove/alter synthetic result only in the disposable fixture and confirm the final status is `UNKNOWN`/blocked, never success. | Missing child code or malformed result becomes success or is misreported as a different failed gate. |

Begin with a small disposable test VHDX and short test deadlines to exercise failure paths. Then observe the actual configured limits within the overall 30-minute session cap. Never fill the VM's OS volume intentionally. Preserve the failed fixture record and stop on the first unexpected behavior. These tests establish only the supervisor/isolation controls; they do not satisfy native F2 A–G or prove Godot readiness.

## 8. Stop conditions, decisions and implementation plan

Immediate `BLOCKED_ENVIRONMENT` / stop conditions:

- No already-provisioned disposable VM can meet the offline/no-clipboard/no-writable-host-share, standard-user, disk-cap, resource-limit and external-timeout requirements without installing features, elevating, or weakening host protection.
- Sandbox remains the only candidate and CPU, disk, or whole-session hard ceilings cannot be enforced and observed.
- Any process escapes Job Object supervision, a requested limit cannot be set/query-verified, a child survives timeout/cancel/supervisor loss, the VM watchdog is missing, or token identity is ambiguous.
- The fixed-size virtual storage grows beyond its configured bound, guest writes escape the disposable volumes, or host inputs are writable/changed.
- Godot's exact official build/hash is unavailable, its actual process token is not standard-user, its renderer is not proven GL Compatibility with vGPU disabled, or evidence cannot be safely captured and reviewed.
- Any network path, extra device/redirection, secret exposure, unexpected process, vendor installer, missing expected hash, or uncontrolled write appears.

Proposed ordered work after this design is independently reviewed:

1. **Owner environment decision:** accept or reject the pre-provisioned throwaway VM route. Owner supplies a disposable offline VM only if it already exists without host feature/admin changes; otherwise remain blocked. Confirm disk layout, effective Hyper-V/VM limits, no network adapters, no enhanced-session integrations, and exact read-only input channel.
2. **Supervisor implementation review:** implement only the guest-local allowlisted Job Object controller and inert fixtures on a separate scoped branch; no vendor binaries. Submit source for independent review before any guest execution.
3. **Owner-approved inert qualification:** run the fixture matrix in the named disposable VM, capture actual effective settings and teardown behavior, then close/discard normally. Any failed requirement blocks; source-only test passes do not promote observed gates.
4. **Renderer and token gate:** only after all safeguards pass, follow the bounded official Godot 4.7.2 GL Compatibility and actual process-token procedure above. Keep the project free of Voxel Tools for renderer-only verification. Preserve Issue #26's native A–G ordered gates, archive preflight, approved pins, and stop rules before any later extension load.
5. **Evidence, independent review, owner decision:** submit exact immutable SHA and sanitized evidence; independent evaluator reviews the same artifacts; owner confirms GUI evidence/disposal and separately decides the next stage. No automatic merge or readiness promotion.
