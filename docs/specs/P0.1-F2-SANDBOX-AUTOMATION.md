## Scope and security boundary

The owner can double-click `tests/f2_runtime/provisioning/Launch-F2SandboxReadiness.cmd`, review the host scope dialog, and accept it. No guest command entry is needed. The launcher verifies inputs and config, writes a GUID-named `.wsb` in the current user's TEMP directory, then invokes the Windows Sandbox host executable. The automation template has one exact `LogonCommand`, which invokes the hash-pinned guest bootstrap from the read-only mapping.

The automation template keeps Networking, ClipboardRedirection, VGpu, audio, video, and printer redirection disabled; ProtectedClient stays enabled; the only mapping is `C:\F2-Approved-Inputs` to `C:\F2Input` with `ReadOnly=true`; `MemoryInMB=8192` remains only an allocation. The host preparer requires the exact LogonCommand and refuses any extra or changed command, mapping, root setting, writable mapping, reparse path, or unknown staged file.

The exact LogonCommand starts Windows PowerShell with `-NoExit -Command`. Its first action prints `F2 DIAGNOSTIC STARTING` before invoking the pinned bootstrap, so a missing or unparsable script leaves the PowerShell window open with the startup banner and PowerShell error visible. The bootstrap immediately prints its own entry banner and stage markers. Its catch path displays the failure stage, sanitized error category/type, child exit code when available, fail-closed status, and unresolved diagnostic gates; it does not print exception messages or credentials. The console remains open at the PowerShell prompt until the owner closes the window or closes Sandbox. No guest command is needed.

Windows Sandbox runs the LogonCommand under its container user, normally `WDAGUtilityAccount`; Windows Sandbox documentation says mapped folders are available before the LogonCommand runs and recommends putting multistep startup work in a mapped script. The bootstrap therefore uses this initial account only to create a unique temporary local user **inside the disposable guest**, then launches the pinned diagnostic under that user. It never creates a host account. The generated password uses the system cryptographic RNG, is held as a `SecureString` only in the guest bootstrap process, and is not written to a file, command line, output, configuration, or PR. If account creation, credential launch, or token verification fails, the report is `BLOCKED_STANDARD_USER`; it never falls back to running the diagnostic as the administrator. [Microsoft Windows Sandbox configuration reference](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file)

The standard-user diagnostic reports the actual identity, `WindowsPrincipal.IsInRole(Administrator)`, the `whoami /groups` Administrators row, active adapters and IPv4/IPv6 default-route counts, mapped-folder write denial, graphics adapter names, and explicit UNKNOWN for GL Compatibility, enforced CPU/disk/time limits, evidence export, and Sandbox discard. The result window remains open until the owner closes it. The child diagnostic process has a 60-second timeout; this bounds that process only. It is not CPU/disk supervision or the separate five-minute-per-probe / 30-minute-session watchdog recommended in Issue #26. That complete external supervision is still UNKNOWN; if it cannot be enforced in Sandbox, use an owner-provisioned throwaway VM rather than loosening isolation. Guest-local temporary output files are removed after parsing. No writable host output mapping or clipboard transfer is used. F2 native runtime remains `NOT RUN`.

```text

```
