## Prepared files

- `tests/f2_runtime/provisioning/Prepare-F2SandboxInputs.ps1` checks host executable presence without launching it, tries a read-only feature-state query, validates the exact `.wsb` safety settings and diagnostic script digest, and optionally stages the one reviewed plain-text script in the fixed `C:\F2-Approved-Inputs` directory. It refuses profile/worktree/root/reparse paths and unexpected files. It does not delete pre-existing files or overwrite a different diagnostic.
- `tests/f2_runtime/provisioning/Get-F2SandboxReadiness.ps1` reports guest identity and `whoami /all`, current admin membership, adapters and IPv4/IPv6 default routes, read-only mapping behavior, OS and graphics inventory, visible RAM/disk, and explicit UNKNOWN states for actual Godot launch identity, GL Compatibility support, enforced CPU/disk/time supervision, and evidence export/discard.
- `tests/f2_runtime/provisioning/F2-Isolated-Sandbox.wsb.example` remains the reviewed static configuration: networking, clipboard, vGPU, audio/video, and printer redirection disabled; ProtectedClient enabled; only `C:\F2-Approved-Inputs` mapped read-only to `C:\F2Input`; 8192 MiB memory allocation. The memory value does not supervise CPU, disk, or time.

The fixed host folder was created and now contains only the reviewed guest diagnostic script. Its SHA-256 over strict UTF-8 text with normalized LF line endings is `5677f096eb78c2db08f5630e53a74c932719130ca0f7842ee8dca2ac2c0ff300`; this stays stable if Windows checks out the PowerShell file with CRLF endings. Keep this narrow input in place only for the owner's manual Sandbox check; remove it using the exact-path rollback below after evidence capture if desired.

The guest diagnostic attempts to create a uniquely named temporary file in the mapped directory to confirm write denial. If the write unexpectedly succeeds, it removes that file and reports FAIL; stop immediately and inspect the host folder. The test scope is limited to this dedicated one-script directory.

## Owner procedure

First inspect the scripts and `.wsb` text. From a normal PowerShell prompt in the repository, run the non-mutating checks:

```powershell
pwsh -NoProfile -File tests/f2_runtime/provisioning/Prepare-F2SandboxInputs.ps1
```

To create only the fixed narrow input directory and stage the pinned diagnostic script, run:

```powershell
pwsh -NoProfile -File tests/f2_runtime/provisioning/Prepare-F2SandboxInputs.ps1 -PrepareInputs
```

If Windows denies creation at `C:\`, stop and have the owner arrange the directory deliberately; do not run the command elevated merely to bypass that boundary. If `Containers-DisposableClientVM` is UNKNOWN, an owner may inspect it from their own Administrator PowerShell, but this script never requests elevation or changes the feature.

After `approved_input_staging` is PASS, make a local `.wsb` copy of the checked example, inspect the complete text, and open it manually:

```powershell
Copy-Item tests/f2_runtime/provisioning/F2-Isolated-Sandbox.wsb.example "$env:TEMP\F2-Isolated-Sandbox.wsb"
notepad "$env:TEMP\F2-Isolated-Sandbox.wsb"
```

Confirm the content is unchanged, then double-click that `.wsb` file in Explorer. Capture a screenshot showing the Sandbox guest opened. Do not use `LogonCommand`; this task does not auto-run anything. If the window does not open or any setting differs, record `BLOCKED_ENVIRONMENT` and stop.

Inside the guest, manually open PowerShell and type:

```powershell
& 'C:\F2Input\Get-F2SandboxReadiness.ps1'
```

Capture the full JSON console output in a screenshot. Keep clipboard redirection off; do not export through a writable mapped folder. The guest output and owner screenshot should be attached to the owner’s evidence record.

## Decision rules after owner observation

- A FAIL in guest identity/admin status, adapter/default-route observation, or mapped-folder write denial is a stop. Do not stage or run any native payload.
- PASS for no active network adapter/default route is limited to those observations; the owner must also confirm the effective Sandbox configuration and no alternate network path.
- The guest's `godot_standard_user_launch_context`, `graphics_inventory.godot_gl_compatibility`, `resource_and_supervision_limits`, and `evidence_export_and_discard` checks are intentionally UNKNOWN. Resolve them with observed evidence. Do not mark standard-user launch ready based only on `WDAGUtilityAccount`, the current PowerShell token, or a configured memory allocation.
- Godot GL Compatibility is not tested here. If it cannot be demonstrated with vGPU disabled, report `BLOCKED_RENDERER`/`INCONCLUSIVE`; do not enable vGPU or fall back to host execution.
- Only if every Issue #26 isolation, standard-user, renderer, resource/time supervision, evidence, and cleanup gate has observed passing evidence may a separate owner record say `READY_FOR_STAGING`. This issue does not download or launch vendor code and does not authorize the next execution step by itself.
