# F2 G1 ACL evidence capture

## Scope

This tool captures a read-only ACL baseline for VM `F2-G1-Isolated-Disposable` (`6f8d61ce-7c08-4c48-82d9-5fa7fe40a7b1`) and the 11 previously identified objects under `G:\F2-G1-Isolated-Disposable`. It does not change ACLs, VM settings, files on G:, registry values, switches, or disks. It never starts a VM.

The elevated child requires the exact VM ID, name, and `Off` state; identifies the Kingston device by serial `152D20337A0C` uniquely across `Win32_DiskDrive`, `Get-Disk`, and `Get-PhysicalDisk`; validates model, USB bus, health, G: partition mapping, and NTFS; verifies configured VM paths; and rejects missing paths, aliases, and reparse points. Model validation uses all three raw model fields: the anchored Win32 form accepts only the exact Kingston model with an optional terminal `USB Device` suffix after whitespace collapse; `Get-Disk.FriendlyName` must canonicalize to `KINGSTON SA400S37240G`; and `Get-Disk.Model` must canonicalize to `SA400S37240G`. Raw and normalized forms are retained in the evidence. Any failed gate prevents ACL reads. For each of the exact 11 canonical paths, it rechecks the no-reparse path chain immediately before reading the owner/group/DACL SDDL through Windows security APIs. SACLs are not requested. The SDDL parser records each supported allow/deny ACE, mask and inheritance flags; an unsupported ACE type fails that object closed.

After the 11 ACL reads, the collector re-queries the same VM ID and verifies its name and `Off` state, rechecks the exact configuration/checkpoint/smart-paging/VHDX paths and zero NIC count, repeats the serial/model/USB/health/G: mapping checks, and rechecks all 11 paths for reparse points. `Complete` is false unless the final observed VM state is `Off` and every required initial and post-collection gate is present exactly once and passes. The document records the final observed state rather than assigning `Off` unconditionally. Both the collector's completion flag and the host evidence validator require the structured post-collection VM, path, NIC, and storage snapshot; the host independently recomputes the VM/path and Kingston checks and compares the initial and final storage identity observations. Missing post evidence, duplicate/missing gates, or changed final identity/path/storage values fail closed.

## Captured evidence

Each object record contains canonical path, owner and owner SID, raw SDDL, DACL protection, PASS/FAIL and error, ACE count, and every ACE's principal, SID, allow/deny type, rights, access mask, inheritance and propagation flags, and inherited status. The document includes the exact expected path list, record/ACE/error counts, preflight gates, disk identity summary, per-record SHA-256 values, a records manifest digest, and a SHA-256 digest over the exact UTF-8 payload bytes.

## UAC boundary and bounded result handoff

The standard-token launcher generates a random capture ID and derives the mailbox path directly below the Windows CommonApplicationData directory (normally `C:\ProgramData`). It does not create the directory. The elevated coordinator validates the full CommonApplicationData ancestor chain, owner, DACL, volume, and non-reparse path, then creates the unique mailbox atomically with a protected DACL owned by BUILTIN\\Administrators. SYSTEM and BUILTIN\\Administrators receive inheritable Full Control; the requesting SID receives inheritable ReadAndExecute only. An inheritable OWNER RIGHTS ACE also limits the file creator's implicit owner rights to ReadAndExecute, which matters when same-account UAC makes the standard requester SID the owner of files created by the elevated process. On the parent and its ancestors, untrusted `DELETE_CHILD`, `DELETE`, `WRITE_DAC`, `WRITE_OWNER`, GENERIC_WRITE, and GENERIC_ALL grants are rejected. Narrow parent create/metadata rights are evaluated separately: the observed BUILTIN Users `0x116` ACE is accepted on the protected parent because it grants add-file, add-subdirectory, write-EA, and write-attributes, but not authority to remove, replace, or retake control of an existing mailbox. The mailbox DACL is set at atomic creation and must be protected, so those parent ACEs cannot inherit into it. Any other mismatch fails closed; there is no LocalAppData or G: fallback. The coordinator launches under UAC, reads its actual Windows identity and administrator role, and binds the requester's SID to the request. It accepts either the same user elevated or a different credentialed account that is actually in the local Administrators role. A non-administrator, an account unable to read the pinned worktree, or an unsafe CommonApplicationData ACL fails before VM/storage inspection with an actionable error. Start UAC from a standard, non-elevated PowerShell session; approve the prompt or supply an Administrator account when Windows requests credentials.

### Mailbox-parent ACL semantics

The observed `C:\ProgramData` DACL is `O:SYG:SYD:PAI(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)(A;OICIIO;GA;;;CO)(A;OICI;0x1200a9;;;BU)(A;CI;DCLCRPCR;;;BU)`. Parsing it with Windows `RawSecurityDescriptor` yields the BUILTIN Users creation/metadata ACE mask `0x00000116`; it does not contain `FILE_DELETE_CHILD` (`0x40`), `DELETE` (`0x10000`), `WRITE_DAC` (`0x40000`), or `WRITE_OWNER` (`0x80000`). Microsoft defines directory mask `0x2` as adding a file and `0x4` as adding a subdirectory. The remaining set bits are write extended attributes and write attributes on that directory. These rights allow a pre-creation collision/denial of service, but do not by themselves authorize deleting or replacing a child. The capture name is random; even if an attacker races or guesses it and pre-creates it, `CreateDirectoryW` fails on the existing object and the coordinator does not adopt it.

The mailbox itself is accepted only when it is non-reparse, Administrator-group-owned, has the exact four-ACE protected DACL, and gives the requester ReadAndExecute only (including the OWNER RIGHTS ACE). A protected DACL prevents parent ACE inheritance from changing that child DACL. The coordinator also inspects each existing ancestor through the volume root for dangerous allow ACEs and untrusted owners, and requires the mailbox parent DACL to be protected. This is a conservative descriptor-level policy, not a complete effective-access computation for arbitrary tokens, nested groups, privileges, central access policies, or filesystem filter drivers. The regression fixtures use the observed SDDL and synthetic attacks; they do not create an actual alternate user token or constitute live host-token authorization evidence.

Microsoft references: [file and directory access rights](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights), [file access-right constants](https://learn.microsoft.com/en-us/windows/win32/fileio/file-access-rights-constants), [ACE inheritance](https://learn.microsoft.com/en-us/windows/win32/secauthz/ace-inheritance), and [ACE inheritance rules](https://learn.microsoft.com/en-us/windows/win32/secauthz/ace-inheritance-rules).

There is no named-pipe IPC across the UAC boundary. In particular, production does not use `PipeOptions.CurrentUserOnly`: on Windows that option checks both user identity and elevation level, and the enum member is also absent in Windows PowerShell 5.1. Once elevated, the coordinator starts a collector worker without another `RunAs`, so both share the coordinator's token. The elevated coordinator launches the worker through the production `-EncodedCommand` path with redirected stdout/stderr and asynchronous bounded readers. One monotonic `Stopwatch` deadline covers the complete worker process and both stream drains, even after the worker process exits. At deadline, the coordinator marks any pending reader incomplete, requests worker termination if needed, waits only for the configured bounded cleanup grace, and closes redirected streams without awaiting pending reader tasks. Reader, stream-disposal, process-disposal, or termination errors remain explicit and make `OutputComplete`/`CleanupComplete` false. The coordinator records worker PID/state, actual exit code when available, elapsed time, timeout, stream hashes and observed lifecycle stages even when the ACL frame is absent. A bootstrap wrapper emits a bounded fatal error when the pinned script invocation fails before its internal collector catch can run. The worker writes its bounded framed ACL payload and bounded PowerShell stream log to unique, create-new mailbox files. The coordinator records both expected artifact states before parsing either file, then publishes separate bounded stdout/stderr diagnostic documents in the protected mailbox. The diagnostic file hashes are bound into the completion integrity manifest. Missing stages, missing files, nonzero/unknown exit, timeout, lingering readers, cleanup failure, truncated or incomplete output, or failed diagnostic publication remain `INCOMPLETE`; no partial diagnostics can be accepted as a baseline. The coordinator checks exact lengths, frame digest, JSON schema, record manifest, source pins, all target gates and the worker's actual process exit before atomically publishing `coordinator-status.json` last. The standard-token launcher waits on the elevated coordinator process handle, captures its actual exit code, verifies the protected mailbox DACL and reads only bounded non-reparse files, compares coordinator status to that actual process exit, verifies source pins and hashes, and independently validates the complete 11-object payload before returning `COMPLETE_READ_ONLY_ACL_BASELINE`.

The two earlier authorized captures remain **root-cause UNKNOWN**: only coordinator status files survived, both report a missing ACL frame, and neither contains worker stream data. Source inspection did confirm a separate early-worker defect: the `CollectorChild` catch attempted protocol-module logging helpers even when failure occurred before module import. A non-elevated production-script test with an intentionally wrong pin reproduced that dependency failure without reaching Hyper-V or reading ACLs. The revised worker catch serializes a bounded diagnostic using built-in PowerShell/.NET operations and the same protected mailbox path; this reproduces a defect class but does not prove it caused either earlier live failure.

All mailbox writers refuse overwrite, use a temporary CreateNew file followed by an atomic same-directory move, and cap output sizes. The parent rejects missing, duplicate, oversized, reparse, short, malformed, hash-mismatched, status/payload-inconsistent, or nonzero-exit results. If UAC is canceled, a child fails, or the coordinator exceeds its outer deadline, the launcher reports an incomplete result and never treats it as success. The standard-token parent does not try to terminate a high-integrity process across the elevation boundary; if the coordinator remains alive at its outer timeout, it reports `StillRunningAtTimeout` and does not accept evidence. The coordinator's worker/stream helper has no unbounded process wait or asynchronous-reader join: process termination gets a finite cleanup grace, and lingering readers are abandoned and recorded as incomplete.

Only a complete validated payload is saved. Before elevation, the parent requires a clean worktree at the caller-supplied reviewed commit and verifies launcher/module hashes against the committed `F2_ACL_SOURCE_PINS.json`. It opens all three files with read-only, write-denying handles and retains them until the coordinator exits. The elevated coordinator verifies both executable source hashes before importing the protocol module or collecting host data. The evidence path is checked from its existing ancestors through the volume root for reparse points; Win32 volume GUIDs must prove the evidence volume differs from G:. A new CommonApplicationData child is created atomically with the exact protected DACL above and the Administrators group as owner. Payload, stream and integrity files are written through bounded CreateNew temporary names and atomic renames, with the integrity document published last as the completion marker. Existing paths are never overwritten. SHA-256 provides integrity checks against accidental corruption; provenance is additionally protected by the requester having read-only access to both the mailbox and its parent during transfer.

The ACL reader intentionally supports only ordinary `CommonAce` allow/deny entries with inheritance flags. It fails the object closed if it encounters object ACEs, callback/conditional ACEs, audit ACEs, unknown ACE classes, or unsupported flag bits, because omitting object GUID or callback semantics would make the evidence incomplete.

## Approved live capture procedure

After the owner explicitly authorizes one bounded read-only capture phase for the exact independently reviewed commit, run with that full 40-character SHA:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\f2-acl\Invoke-F2AclReadOnlyCapture.ps1 -ExpectedCommitSha <reviewed-commit-sha>
```

The command requests UAC for the read-only coordinator. If Windows requests alternate credentials, use an Administrator account; the collector verifies that account's actual administrator role and the requester SID. Keep the VM OFF. The elevated worker performs the target-specific preflight and ACL reads, plus one read-only lookup of the exact capability SID in Microsoft's `AllCachedCapabilities` registry value. It stores only whether the exact SID was present, not unrelated registry value contents. No registry value is modified. If a source hash, VM identity/state, disk mapping, path, or evidence integrity check fails, no complete baseline is produced.

The parent must be allowed to finish and return its structured summary, the actual elevated coordinator exit code, and the worker exit code. If the command runner reports a session ID, retain it and poll until the final result; an empty intermediate output is not completion. A timeout, missing mailbox/status file, unexpected process exit, any failed gate, incomplete record set, or integrity error yields `INCOMPLETE` and no successful baseline.

## Security analysis limits

Microsoft documents that the per-VM SID can require access to the VM's configuration and virtual disks, and identifies `S-1-5-83-0` as the Hyper-V Virtual Machines group whose membership VMMS maintains. Microsoft also documents capability SIDs as legitimate Windows security identifiers and warns against deleting capability SIDs from filesystem permissions. The exact necessity of this project's two root-level ACEs for the reported Hyper-V capability is not documented by those generic references. The live ACL can establish their scope and inheritance, but a read-only capture alone cannot prove whether Hyper-V will function without them; the VM remains OFF and no permission change or start test is in scope.

The provisioning transcript shows that the directory was initially created with protected SYSTEM and Administrators ACEs. `New-VHD`, `New-VM`, and adapter removal then ran before the later `Get-Acl`/`Set-Acl` that intentionally added the VM-specific SID. That `Set-Acl` code did not explicitly construct the capability ACEs; it read and preserved the then-current DACL. No intermediate DACL snapshots were recorded, so the command or Hyper-V component that first introduced the capability ACEs remains UNKNOWN.
