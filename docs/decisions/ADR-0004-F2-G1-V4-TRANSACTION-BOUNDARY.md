## Problem discovered in the actual source

The historic installed v2 release is pinned to commit `5741ffe90a3abd02a08563e6431e8a0b9b63eeb1`, active manifest SHA-256 `b5f01570cf8937324f0c763f72a8d05b5532472156d4e5b0fcfbd180dc7abbe9`, and seven exact installed files. The current production updater's `Get-F2UpdateManifestObject` accepts only `v2`/`v3` with an exact seven-member set; `Test-F2UpdateInstalledOldRelease` verifies the historical old state; its recovery logic recognizes the old manifest, candidate v3 and a legacy journal. The runtime, coordinator and launcher still dispatch v3. Draft PRs #73/#74 are unmerged and v3 must not be presumed installed.

The accepted source-only `f2-icacls-runtime-release-v4` contract is **ten** exact package files, including the immutable historical v1 and independently reviewed v2 pin manifests, and `Status=SOURCE_ONLY_NOT_RELEASE_APPROVED`. Those v2 manifests bind the **existing** source module hashes. If we edit production runtime/coordinator/collector but keep these v2 manifests byte-for-byte immutable, a new internally consistent package cannot pass its own nested pins. Reusing the source-only v4 contract as an installable manifest would falsely imply approval and produce identity contradictions.

## Proposed resolution

1. **Freeze the present ten-member v4 as SOURCE_ONLY.** Keep its exact reviewed source/manifest/pins separate from anything installable. Never mutate the old v1/v2 manifest bytes, retained v2/v3 receipts, or signed source history.
2. **Version the new installable runtime contract independently.** Preferred schema: `f2-icacls-runtime-release-v5` after new production code and a new source-pin generation (`*_V3.json` if names are approved). Its exact inventory and cardinality are **not yet frozen** and cannot be assumed to equal the current ten-member v4 set. The version name is a proposal, not an approved schema or an attempt to silently change the existing v4 meaning.
3. **Version the transactional protocol separately:** `f2-protected-update-transaction-v4`. It can describe authorized transitions to an approved future installable manifest without reinterpreting legacy `transaction.ndjson`. State machine, receipt, sealed package and recovery must agree on *one* immutable manifest digest and exact predecessor identity.
4. **Trust bootstrap precedes receipt verification.** Proposed baseline: independently provisioned and enforced Windows code-integrity policy for a signed, locally pinned bootstrap/verifier and administrator-controlled protected trust configuration, independently established BEFORE handling any candidate receipt. The receipt's ReceiptVerifierSha256 is a checked consistency claim, never a root of trust. An external, authenticated **online approval authority** must provide authoritative signing-key status, time and durable replay ledger; no offline signing, expiry, revocation or deployment are considered approved. If the OS policy, platform trust, signer enrollment, authority availability or local protected configuration cannot be independently demonstrated, installation is BLOCKED. The precise signature suite, key custody, independent provisioning process and operator identity remain subject to owner approval; this proposal is not a claim they exist.
5. **Privilege boundary: no Git execution in an elevated installer.** Complete Git/source inspection in a separate non-elevated stage; seal and hash exact package bytes and pass only an independently approved signed receipt plus a trusted, already verified fixed package. Under elevation, independently recheck package bytes, identity, ACL, process quiescence and locks. The source-only pre-dispatch runner's residual `Process.Start()` and descendant-process limitations are not inherited as production guarantees.
6. **Replay bound outside local journal.** A signed receipt must bind the exact single TransactionId, ApprovalId, EnvironmentBoundaryId, predecessor, target digest, operation and expected authority generation. Before ANY local filesystem mutation, an external durable approval ledger must atomically reserve that tuple against prior consumption and rollback. Retry is never a new transaction; unchanged TxId is read-only by default and a new signed operation-specific capability is required for actual recovery. Offline execution without the authority is BLOCKED.
7. **Closed transaction ordering and post-switch completion.** Require remote reservation before creating transaction root; explicit durable genesis, stage/publish intent, predecessor-backup intent and verified backup BEFORE switch intent; same-volume atomic package publication and active pointer replace under enforced quiescence. A future, separately authorized FINALIZE_POST_SWITCH may only append durable proof for an already exactly verified target-active state, without repeating a manifest switch. Default is HOLD/PRESERVE on ambiguity.
8. **No supported production v2/v3 cutover in R3.** Both live and maintenance-mode v2/v3 migrations are excluded. Historical v2 lacks the shared release lease; no OS-enforced mechanism that prevents every direct/late legacy reader has been proven for this host. The future cutover requires a separate owner-approved ADR defining launch inhibition, reader inventory, fixed volume identity, authenticated approval-authority connectivity and verified exit back to normal host operation. Until then any v2/v3 production migration is UNSUPPORTED_PREDECESSOR/REJECT_BEFORE_WRITE. Hypothetical state-machine cases authorize no installation.

## R3 contract limits and reserved owner choices

**Production migration is UNSUPPORTED in this revision.** The v4 transaction model does not install from v2 or v3, even with a credible signed receipt; all install, recover-forward and finalize operations are hypothetical pure conformance cases. ROLLBACK is explicitly **reject-only**, even with a syntactically valid signed-looking rollback receipt. Its implementation requires a separate approved protocol.

**Threat model is proposed, not accepted:** adversarial candidate bytes, unauthorized local changes, receipt replay and rollback of a locally valid journal are in scope; independent OS bootstrap/signing policy and monotonic external authority are assumptions. Privileged OS/policy/signer compromise and external authority rollback are out of current scope. If the owner accepts weaker local-only one-use authorization, record the weaker guarantees in a new ADR instead of silently omitting anti-rollback.

**Durability scope for the only proposed implementation milestone:** read-only pure state-machine harness on temporary, nonprotected fixtures, simulating process termination/failure (tier A). OS crash (B) and power/storage failure (C) are NOT established; even tier A does not authorize a production active-pointer switch. Future File.ReplaceW behavior, backup names, documented failure outcomes, flush semantics, and Windows App Control/PowerShell 5.1 script policy effects need independent review. A machine-wide signed Windows policy has an independent RSA signing chain; the proposed receipt signature uses an independent, owner-unselected key/format.

**Single closed matrix taxonomy:** `inspection_state` and `expected_classification` are separate. `REMOTE_RESERVED_NO_LOCAL` means no local root; `LOCAL_ROOT_GENESIS_INCOMPLETE` means root exists with missing/torn genesis. R3 CONTRACT.md §5.1 is the sole allowed enum; unexpected states fail closed. All defaults are non-mutating. Original R1/R2 BLOCKED reviews remain unchanged.


## Alternatives evaluated

- **A: add `v4` to updater `ValidateSet` and raise 7→10. Rejected.** Breaks historical installed-state validation, source pin generation, journal recovery states and the v3 pinned dispatch; falsely treats source-only approval as release approval.
- **B: rewrite old v1/v2 manifests to include changed runtime bytes. Rejected.** Destroys original historical evidence and contradicts frozen pin provenance.
- **C: keep the v4 source-only contract and introduce separately versioned production manifest + transaction protocol. Preferred.** Makes migration explicit, preserves old releases, allows source-only review and owner-gated release authorization.
- **D: bypass the manifest/pin checks for an initial v4 install. Rejected.** Weakens the very protection being tested and opens silent mixed-version states.

## Formal approval gates before the next operational stage

The specification `docs/reviews/f2-g1-v4-transaction-design/CONTRACT.md` is a design-only fault model; the 92-case matrix is not executable. Required future owner decisions: (a) choose final v5 naming/pins/inventory and predecessor; (b) approve independently enforced platform bootstrap policy and separate policy-signing and receipt-signing trust keys with PowerShell 5.1 compatibility; (c) accept the rollback/replay threat model and independent online approval authority or approve a separately reviewed weaker alternative; (d) select supported storage crash tier and validate actual ReplaceFileW failure/readback outcomes; (e) commission and approve a **new** concrete v2/v3 cutover mechanism/ADR before any migration; (f) separately approve production code, CI, PR, merge, UAC or release. R3 proposes at most a nonprotected read-only synthetic conformance harness after independent review.

The current ChatGPT–GitHub author / Codex–Windows independent-verifier arrangement under ADR-0003 remains **temporary for this blocked F2 G1 cycle**. On explicit owner-recorded closure the original Codex implement+commit → ChatGPT independent review → owner decision model resumes.
