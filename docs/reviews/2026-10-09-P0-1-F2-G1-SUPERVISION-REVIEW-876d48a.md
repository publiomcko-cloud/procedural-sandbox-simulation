Read-only host mapping and zero-network observations are narrow isolation evidence, not whole-guest resource enforcement. No native run is justified in the currently observed Sandbox under Issue #26's hard gates.
2. **Job Object boundary distinguished.** [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) support grouped process constraints and `KILL_ON_JOB_CLOSE`, but apply only to associated processes; notably, Microsoft documents `Win32_Process.Create` subprocesses that are not automatically associated. The plan demands suspended creation, assign-before-resume, non-inheritable handles, no breakaway flags, query-back and inert descendant/escape testing. All are appropriately fail-closed, though they still require actual inert evidence.
3. **VM alternative is conditional, not approved.** A pre-provisioned offline throwaway VM with independent hypervisor CPU/memory limits, fixed virtual disks, a session watchdog, standard-user process tokens, read-only inputs, safe evidence channel and vGPU/clipboard disabled is a valid candidate **only if** each requirement is queried and inert-verified. `Set-VMProcessor -Maximum` exposes a percentage-based limit; user-selected proposal `2 vCPU, 20%` is **not a validated minimum for Godot**. No assertion that a VM is already available.

### R2 — Host watchdog failure mode and effective deadline qualification (spec §3.1 lines 72-83, §7 lines 140-141, §8 lines 153-155)

The design requires an independent host controller to shut down only the named throwaway VM before a 30-minute session limit, yet fails to state what happens when **that host controller itself crashes, is terminated, loses its VM handle, cannot query the target or fails to issue/confirm shutdown**. An independent supervisor with undefined self-failure behavior cannot be treated as an *observed enforced ceiling*. Add a bounded design requirement: fail closed on inability to start and query-back the watchdog; define a separate automatic expiration/lease/fail-safe mechanism or explicitly state `BLOCKED_ENVIRONMENT` until independent protection against watchdog loss is demonstrated. Add an inert fault-injection case for watchdog loss, incorrect VM identity, watchdog missed deadline and confirmed named-guest cessation. Avoid indiscriminate host process termination or host elevation and ensure no concurrent production VM can be affected. This is a **design completeness requirement**, not a demand to implement/watchdog or run it in this docs-only PR.

### R3 — Specify renderer driver evidence and editor-versus-export support (spec §5 lines 112-118; handoff renderer statement)

Godot 4.7's `RenderingServer.get_current_rendering_driver_name()` can return `opengl3`, `opengl3_es`, or `opengl3_angle` for Compatibility paths (and other names for non-Compatibility). Pin recording **both** runtime method `gl_compatibility` and the actual driver string, graphics API/adapter/version and an on-screen GUI; if `opengl3_angle` is observed, verify/log the actual ANGLE underlying Windows D3D11 backend rather than treating the driver string alone as proof. [Godot's system requirements](https://docs.godotengine.org/en/4.7/about/system_requirements.html) document the native-editor Compatibility GPU minimum in terms of OpenGL 3.3; the Windows **native export** row permits OpenGL 3.3 **or D3D11**. State which exact official Godot executable is under test and require separately documented/runtime-proven driver support for it; do not transfer native-export support to an unverified editor process as an assumption. If unsupported, keep `BLOCKED_RENDERER` and do not change to Forward+/Vulkan or enable vGPU. See [Godot RenderingServer](https://docs.godotengine.org/en/4.7/classes/class_renderingserver.html).
