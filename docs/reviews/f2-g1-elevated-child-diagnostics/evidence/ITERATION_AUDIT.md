# Iteration audit — F2 G1 child diagnostics

This is a sanitized source-only audit. It records implementation findings and test-harness corrections. No protected host operation occurred.

| Iteration | Evidence | Correction | Validation |
|---|---|---|---|
| Baseline | PR #61 review `5494765012` confirmed the requester received only the elevated process exit; no child `Stage` or `ErrorCode` was returned. The prior child exit 1 remains unknown. | Added a request/nonce/pin/process-bound single-record local named-pipe protocol and child `finally` publication. | Windows PowerShell 5.1 real same-token process integration exercises the production child builder and pipe receiver. |
| Command-size check | The first builder embedded the complete 24,986-byte protocol module into `-EncodedCommand`. Measured encoded command size was 106,524 characters, beyond Windows' 32,767-character process command-line limit. | Parent now verifies the module bytes; the child reads the fixed source path once, rehashes against the launcher pin, parses, and executes those same in-memory bytes. | Final test records `ProductionChildEncodedCommandCharacters` and checks the encoded content plus a fixed argument reserve against the limit. |
| Exit consistency | A validly framed diagnostic could claim an exit code different from the actual process exit. | The receiver now invalidates and discards a record if its claimed child exit differs from the separately observed process exit. | Synthetic cross-process mismatch and forged `Complete`/zero claims are rejected; actual process exit remains reported. |
| Pipe wait failure | The first receiver version returned `CHANNEL_FAILED` immediately if `BeginWaitForConnection` failed, potentially before observing the child exit. | The receiver now enters its bounded monotonic child monitor after this failure and preserves the actual exit or timeout together with `CHANNEL_FAILED`. | A TEMP child exiting 7 against a disposed server verifies bounded status and exact exit retention. |
| Test harness: case-insensitive variables | Initial PS5.1 fixture variables such as `$wrong` collided with `[switch]$WrongRequest`; PowerShell variable names are case-insensitive. | Renamed generated values to `*Flag` variables. | Cross-process test suite passes. |
| Test harness: fixture command size | Embedding the protocol bytes in every synthetic worker also exceeded the command-line limit. | Worker fixtures read the test module by local path; production child builder has its own separate command-size regression. | The production child integration and all protocol negatives pass under Windows PowerShell 5.1. |
| Test harness: false PID claim | The original negative fixture used the real sender PID as the expected PID, so it did not test a mismatch. | Added a distinct TEMP target process and a separate pipe-client process. | Receiver rejects the client PID mismatch and preserves the target process exit. |
| Test harness: missing negative-case inputs | Tamper/duplicate fixtures initially omitted their stage/code values. | Added safe synthetic defaults and retained the explicit no-message case. | Tamper, duplicate and missing cases now reach their intended protocol gates. |

The final full run is recorded in `WINDOWS_PS51_REGRESSION.log`. The iteration-specific first-pass harness failures are not presented as production failures or as evidence about the exhausted UAC attempt.

| Requester error sanitization | Final review found the requester fallback accepted arbitrary uppercase token-shaped exception text, which could include a SID-like value. | Added an exact stable-code allowlist; unknown text maps to UPDATE_UNCLASSIFIED_FAILURE. | TEMP assertions verify approved stable codes pass and raw SID/arbitrary token-like input is suppressed. |

| Final error boundary | Review of requester-side failure output found regex-only acceptance could pass SID-like or arbitrary token-shaped exception text; native pipe initialization could expose unstable system error detail. | Added an exact requester error-code allowlist and mapped diagnostic server initialization failures to UPDATE_DIAGNOSTIC_CHANNEL_FAILURE. | PS5.1 synthetic cases reject raw SID-like/token text, preserve approved stable errors, and verify initialization failures map to the stable code. |

| Test fixture timing | One diagnostic run failed the distinct-client-PID assertion; instrumented rerun passed and exposed no production failure. The expected target fixture exited after only 700 ms, competing with fresh PowerShell startup time. | Extended the synthetic target lifetime to 5000 ms and retained failure-result output, keeping it inside the 10-second receiver bound. | The subsequent complete PS5.1 suite passed with the PID-mismatch assertion and all other cases. |
