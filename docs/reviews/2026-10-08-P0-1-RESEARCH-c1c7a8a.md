## Issues/conditions to close before authorizing implementation spike

H1 (high): GDExtension feature parity. Official upstream documentation says FastNoise2 is not included in the extension. The research report should flag this directly in the candidate A comparison; gate noise algorithm parity and necessary shader/rendering paths with GL Compatibility renderer.

H2 (high): Actual API feasibility of domain-to-Voxel Tools adapter. Vendor internals may own loading, meshing and collider task schedules; the proposal describes epoch/revision publication checks but does not prove the extension exposes every required hook. First stage should be a minimal compatibility/API proof; unsupported callbacks must be explicit capabilities and potential disqualifiers, never silently emulated as guarantees.

M1 (medium): Define shared canonical analytic field, coordinate units/precision, density sign, SDF quantization/tolerance, mesh surface accuracy and hashing layers before claiming bitwise equality across unlike voxel formats. Domain field and journal can be exactly hashed; candidate-specific derived voxel buffers may legitimately differ.

M2 (medium): Keep P0.1's clean edit/save/reopen demonstration distinct from P0.2's atomic multi-region transactions, crash injection, journal durability and migration guarantees. Do not make a full P0.2 persistence system a prerequisite for an initial candidate API smoke.

M3 (medium): Preregister latency sample-count and run independence for p95/p99; 10 repetitions per seed suffice as independent runs but not necessarily for stable high-percentile estimates per workload. Include a minimum observations rule and show confidence/dispersion.

M4 (medium): Wide signed integer region addressing uses a conceptual i64_xyz key; verify Godot Vector3i limitations and any vendor coordinate restrictions before accepting unbounded-region promises. Preserve chunk-relative rendering coordinates.
