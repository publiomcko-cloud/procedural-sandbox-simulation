## Scope and evidence labels

This is a read-only audit of public source, build workflow definitions, GitHub Actions run metadata, release metadata, and the previously accepted F1 archive manifest. No release archive or binary was downloaded, opened, loaded, executed, compiled, or disassembled. No dependency was installed, no maintainer was contacted, and no project runtime/ADR was changed.

Evidence labels used below:

- **Verified source fact** — directly stated by a source file at the pinned commit or an exact dependency license/version file.
- **Verified publisher metadata** — upstream GitHub release or Actions API metadata; a publisher declaration, not an independent binary measurement.
- **Verified release build-log input** — exact checkout, successful compile command, or object/archive named in the public Windows job log for the pinned release run. This establishes build/link inputs recorded by the publisher.
- **Build-path inference** — source selected by the published workflow/configuration for a target, assuming the checked-in workflow and its effective inputs describe the build. It is not direct inspection of the output DLL.
- **Unknown binary fact** — cannot be concluded without a cryptographically connected build manifest/SBOM or binary examination, neither available/authorized here.

The accepted F1 manifest records the v1.7x archive as 54,457,774 bytes with publisher SHA-256 `600737572a5e25541ba6f503e842a3717ba19afafa5474510a6ceff995a1d2d8`, 34 archive entries, and no separate third-party notice files; it reports both Windows x86_64 editor and template-release DLL mappings. Those are historical F1 developer evidence, not a fresh artifact check. See `docs/artifacts/P0.1-F1-artifact-manifest.json` and `docs/artifacts/P0.1-F1-static-inspection.md`.

### Interpreting the source matrix

The job logs move SQLite, LZ4, meshoptimizer, FastNoiseLite, and godot-cpp from source-selection inference to **verified release build-log compile/link inputs** for each Windows target. The package-artifact digest match connects the workflow's assembled package to the publisher-reported release digest. These facts still do not establish which machine code is retained in each final DLL after optimization or identify all runtime/transitive dependencies.

FastNoise2 differs: the GDExtension SCons entry point does not register its module-only option or invoke its module source integration, and the component does not appear in either logged final-link input list. This supports exclusion from these two build paths. A binary scan was not performed.

## License notices and unresolved obligations

The release packaging workflow copies the Voxel Tools `LICENSE.md` into the addon package and does not have a step to copy the listed LZ4, meshoptimizer, FastNoiseLite, SQLite, FastNoise2, or godot-cpp notices. The accepted F1 archive manifest reports no separate third-party notice files. The workflow itself packages the addon source/docs and binaries, but this is a publisher packaging design fact, not a legal conclusion.

The successful Windows build logs explicitly pass LZ4, meshoptimizer, FastNoiseLite, and godot-cpp inputs into the final linker commands. Their notice-retention conditions are therefore **concretely implicated by the recorded build inputs**, and the package workflow copies only the project's `LICENSE.md`; the accepted F1 manifest lists no separate third-party notices. Treat this as a potential redistribution-notice gap requiring owner/legal-risk review. SQLite core's public-domain dedication means a copyright/permission notice is not a condition of distribution. FastNoise2 has no input in either final link command, so its MIT notice is not implicated for these logged targets. No statement of infringement, compliance, or legal entitlement is made from log evidence alone.

Before any project distribution or F2 dependency adoption, obtain one of:

1. A per-target upstream SBOM/link manifest with exact input revisions and a cryptographic digest/attestation connecting it to the two v1.7x Windows DLLs and release asset; or
2. Written upstream confirmation answering the questions below, followed by independent reconciliation against the archive inventory and notices.

If definitive binary evidence remains unavailable, an owner and legal-risk reviewer must decide whether to block distribution, require upstream to issue a corrected/provenanced package, or commission a separately authorized technical examination and assemble a conservative notice bundle. Adding notices alone does not resolve unknown linkage/provenance.
