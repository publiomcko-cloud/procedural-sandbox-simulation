# P0.1 Terrain Backend Comparative Research

**State:** Research report; no backend selected. Companion to the proposed adapter contract and ADR-0002.
**Repository state checked:** 2026-10-08; assigned branch `feat/p0-1-terrain-research`; base `581ce8f0c34cab84e1f0296a83f0ef14422f0038`, also verified as live `origin/main` at research start.
**Source review date:** 2026-10-08. No third-party package was installed, downloaded, built, or executed for this report.

## Executive summary

Candidate A, Zylann's Godot Voxel Tools, already documents smooth SDF voxels, Transvoxel meshing, LOD, edit tools, streaming, and background work. Its MIT license is permissive subject to retaining notices. As checked on this date, its release page lists Voxel Tools 1.7 (GDExtension release `v1.7x`, abbreviated source commit `75d3c6d`) for Godot 4.5+, and a separate custom module build paired with Godot 4.7.2 (`ed1daf0bf`). The project documentation says GDExtension is newer and less tested than the module. This makes A a promising benchmark candidate, but does not establish exact-package operation, export coverage, production suitability, or crash-safe integration.

Candidate B, a custom SDF field store with chunked mesh extraction, can align its data model, revisions, edit journal, and generator versions directly with this project's authoritative simulation state. It avoids adopting another terrain framework, but makes this project responsible for algorithms and systems that A already supplies: meshing, LOD stitching, collision updates, streaming, edit semantics, and persistence. A GDScript-only first experiment avoids a native dependency but has unmeasured throughput risk. An optimized native implementation would reintroduce build, ABI, packaging, licensing, and maintenance costs. No performance claim is measured here.

**Recommendation for owner consideration:** approve only a reversible, isolated, side-by-side P0.1 experiment after approving the exact A artifact/license inventory and the candidate-independent adapter proposal. Keep the production backend undecided until correctness gates pass and both candidates run the same workload on the declared target hardware. Do not treat either package-level compatibility labels or this desk research as acceptance.

## Per-candidate assessment

### A. Voxel Tools

**Verified facts:** The public repository describes a C++ voxel module and now also a GDExtension. The current release page reviewed lists Voxel Tools 1.7 GDExtension `v1.7x` (source commit shown as `75d3c6d`) and a custom Godot 4.7.2/Voxel Tools 1.7 build (`ed1daf0bf`). The repository license is MIT. Documentation covers smooth SDF, Transvoxel, LOD terrain, `VoxelTool` editing, texture channels, streams, SQLite, and threaded work. The same docs warn GDExtension has had less testing than the module; release builds are snapshots in a continuous-development project, not necessarily a stable compatibility guarantee. LOD data editing is limited to the first LOD, and asynchronous saves need lifecycle handling.

**Assumptions:** the GDExtension remains the most practical comparison path to preserve the standard Godot engine distribution. Its public SDF/material buffers could be bridged through an adapter without persisting backend-owned state as the world authority.

**Risks:** native binary ABI/platform packaging; release cadence and maintainer concentration; undocumented/project-specific worker and resource interactions; backend save schema/coordinate limits; first-LOD-only editing; shader/seam setup; data/material mapping; licensing of all bundled/transitive assets; exact engine/export compatibility.

**Missing evidence:** actual release asset target list/checksums and project compatibility test; exact GDExtension 1.7 smoke on Godot 4.7.2 stable; export templates and CI/platform coverage; close/reopen durability under interruption; edit revision and border behavior; representative edit/collision/streaming performance.

### B. Custom SDF terrain

**Verified facts:** Godot provides mesh/resource APIs and worker-thread facilities, but engine resources and scene interaction have thread-safety restrictions. The project's accepted architecture already requires immutable background results, main-thread resource integration, chunk revisions and stale-publication rejection.

**Assumptions:** an initial experiment can use GDScript for the scalar field, extraction, and buffers to quantify the cost of avoiding native dependencies. A production implementation could later use a reviewed optimized implementation without changing the adapter, subject to a separate dependency/ADR gate.

**Risks:** implementation scope is easy to underestimate; ambiguous-case holes, self-intersections, cracks, normal/attribute seams, collision cooking spikes, dense-field memory growth, near-surface edits crossing unloaded regions, LOD consistency, and GDScript throughput. A native optimization could erase the presumed distribution simplicity.

**Missing evidence:** no algorithm, benchmark or prototype exists. Exact voxel resolution, chunk dimensions, mesh extraction algorithm, transition policy, material interpolation, collider granularity, SDF encoding and persistence format remain open.

## Comparative benchmark plan (not run)

This is a preregistration proposal for the later implementation spike. The measurements below are expected outputs, not results. Do not start it until the owner approves the exact dependency/artifact and target environment.

### Controlled environment

Record before the first run: Windows version/build (or the owner-selected shipping OS), CPU model/core count/power profile, RAM capacity/speed, GPU model/VRAM/driver, storage model/filesystem, Godot exact version/build/hash, renderer, display resolution/refresh, project export/debug mode, backend source tag/commit/artifact SHA-256, backend settings, and background process policy. Use the same physical machine and power/thermal state for A and B, AC power, fixed OS power profile, no other workloads, and the same clean project/import cache policy. Capture ambient/thermal or CPU frequency throttling if available. If shipping platforms include multiple classes, run the same suite on the declared minimum and recommended target machines; do not generalize one machine's result.

The owner must choose and document minimum/recommended target hardware and shipping platforms before measurements. If the exact Voxel Tools artifact lacks one of those platforms, record A as unsupported there rather than silently replacing it with a different build. The research checkout is Windows x64, but that is not itself an accepted shipping-hardware decision.

### Matched fixture and run protocol

- Use identical adapter inputs, physical bounds, material registry, edit commands, LOD/viewer path, collision request policy, render settings, and saved output state. Candidate-specific block/chunk settings may differ only to meet the same adapter-visible quality profile; document every setting.
- Pin `Godot 4.7.2.stable.official.ed1daf0bf` for the first comparison. If candidate A cannot run on this standard build and requires its custom engine, mark that exact compatibility failure and request an owner decision; do not compare results from different engine builds as a clean A/B.
- Use fixed test seeds `0x0000000000000001`, `0x00000000000C0FFEE`, and `0x5EED2026`; pin generator schema/version and deterministic fixture inputs. The same complete command trace runs 10 times per seed and candidate after 2 warm-up runs. Save cold-start runs separately; do not blend them into steady-state percentiles.
- Fix logical domain region size at 16 m per axis and sample pitch at 0.5 m for the first test profile (32 intervals per axis; backend internal chunks may subdivide). Record this as a benchmark profile, not a product resolution decision. First demonstrate equivalent surface error against a shared analytic SDF reference within a predeclared tolerance; if either candidate cannot meet that tolerance, report the accuracy/performance tradeoff as a Pareto curve over matched quality profiles.
- Run serialized, never concurrently, with no build/import process in the measurement window. Use monotonic high-resolution timing and the same profiler capture settings. Preserve machine-readable raw samples, logs, canonical field/edit hashes, screenshots, and exact commands/configuration.
- Report median, p95, p99, maximum, sample count, and dispersion for latency; report mean and p95 frame time plus 1%/0.1% low FPS where the capture method supports it. Include per-seed rows and pooled results; never hide outliers.

### Required workloads and outputs

| Workload | Repeatable action | Expected measurements / correctness output |
|---|---|---|
| Deterministic field | Generate/query analytic surface, closed cave loop, and overhang field; permute region request order and restart process. | Samples/sec; generation latency/region; p50/p95 query latency; bytes per region; canonical density/material hash; exact mismatch count. |
| Local edit | Apply 100 scripted add, subtract, smooth/sculpt and paint strokes of fixed radii/positions; include one stress stroke crossing 8 logical regions. | Command acceptance/rejection; commit latency; request-to-visible mesh and request-to-active collision latency; per-frame spikes; regions and bytes rebuilt; expected final field hash. |
| Border/seam | Repeated strokes cross face, edge, and corner adjacency; inspect at equal LOD then across LOD boundary; move viewer through boundary. | Gap/overlap and normal discontinuity counts under declared tolerance; stale result count and whether rejected; neighbor invalidation set; render/collision revision mismatch duration. |
| LOD/edit | Traverse three fixed radii around the edit site, request low LOD, edit canonical full-res data, return to high detail, repeat 50 times. | Requested-vs-published LOD, edit eligibility/explicit rejection, seam defects, latency, memory by LOD, field/collision hash at return. |
| Streaming walk | Deterministic 10-minute scripted camera path with fixed speed and warm/cold cache passes; fixed viewer radius and collision policy. | Frame times, loaded/requested/pending region counts, request queue depth, throughput, stale/cancel counts, peak and steady resident memory, backend bytes and node/resource counts. |
| Save/restore | Apply fixed edit trace, request explicit save completion, unload/reload affected regions, clean process exit, restart and replay/load. Repeat 20 times per seed. | Save/flush time, serialized bytes, reload time, exact canonical field/material/edit hash equality, missing/duplicate edits, storage growth. This is not a crash-consistency test. |

For performance interpretation, separate CPU generation, mesh extraction, main-thread resource publication, collision cooking, renderer/GPU, storage, and wait/queue time where instrumentation allows. Report instrumentation overhead and run an unprofiled timing pass too. No source documentation timing number substitutes for these measurements.

### Correctness gates and threshold-setting method

Before comparing, require zero unexplained field-hash mismatches for the declared deterministic scope, zero unhandled border gaps/overlaps, zero stale result publications, no committed edit missing after orderly save/reopen, and mesh/collision publication that eventually matches committed revision. Use a shared analytic field and geometric tolerances set before viewing candidate output. Any intentional approximation (especially LOD collision or material blending) must be quantified and owner-approved.

There are no accepted numerical performance/memory budgets today. Before results are disclosed, owner and evaluator should set target-derived thresholds from: (1) project target frame rate and its per-frame terrain budget; (2) maximum acceptable interactive edit response; (3) target machine memory budget shared with simulation/rendering; and (4) expected edit/streaming frequency. Record exact numeric thresholds and their derivation in the benchmark issue/PR before unblinding candidate labels. If the owner cannot set values up front, first conduct a labeled pilot to characterize distributions, then have the owner set thresholds and rerun the frozen suite. Never tune thresholds after seeing which candidate wins.

Compare candidates against the same thresholds and quality profile. A candidate passes only if it clears every correctness gate and its predeclared p95/p99/max budgets on each required target. If neither passes, report both and recommend another experiment; don't reduce quality or hardware assumptions post hoc to declare a winner. No benchmark has been executed for this report.

## Integration constraints applying to either choice

1. Domain state and mutation receipts are authoritative. Nodes, meshes, collision shapes, GPU textures and backend caches are rebuildable projections.
2. Every field query identifies world UUID, world generator manifest, stable integer region key, world-space/fixed-point position convention, and edit revision. Density sign is normalized at the adapter boundary (project proposal: positive means solid, matching the baseline architecture proposal; confirm sign before implementation).
3. Every edit is validated against expected region revisions and stable material IDs, journaled atomically across all affected regions, and invalidates every dependent render/collision result.
4. Asynchronous work is stamped with backend instance epoch, request ID, region key, source revision(s), LOD, and halo dependency revisions. Stale or unloaded results never publish.
5. Mod-facing API exposes versioned material/property definitions and validated edit/query commands only; it never returns backend buffers, node paths, classes, or persistence internals.

## Recommended next experiment

After independent evaluation of this research and owner approval of an ADR scope, run an isolated dual-adapter spike using the same deterministic 3D SDF fixtures and benchmark harness. Candidate A must use one exact release artifact whose license, checksum, platform matrix, and engine version are recorded. Candidate B should first be a deliberately bounded GDScript implementation to establish the no-native-dependency baseline. Both must implement the shared contract, cross-region add/subtract, cave topology, a border edit, LOD transition/edit, mesh/collision publication, and serialized edit replay. Add a separate native optimization only if measured B CPU cost misses owner-set limits and the owner approves that dependency/maintenance decision. Do not select a production backend in this research PR.
